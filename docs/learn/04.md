# 04 · Public app exploitation

Inspect a web application firewall finding against the telemetry of a fictional public application.

**Track** Intermediate · 12 min · Cloud

**Prerequisites** Be comfortable reading timestamps and network sensor or waf projection fields.

## Investigate

1. Review the clean baseline. Network sensor or WAF projection supplies the exercise evidence.
2. Consider the hypothesis. A blocked request classified as injection on an exposed route merits a review for origin-side impact.
3. Replay the positive fixture and inspect THX-04. Check WAF action, signature family, route and origin status. Look for paired application errors in an owned environment.
4. Compare the noisy fixture. A penetration test or scanner authorized for that service can trip the same rule.

## Rule and evidence

Count at least 1 observation(s) per `user` inside 300 seconds. Each distinct source record can count once.

| Field | Comparison | Value |
| --- | --- | --- |
| `action` | `eq` | `"waf_decision"` |
| `outcome` | `eq` | `"blocked"` |
| `observables.signature_family` | `eq` | `"injection"` |

Review the following event-level exclusions before changing the rule.

- `observables.authorized_scan` eq `true`

Tuning guidance. Restrict approved-test exceptions by source and time. Retain blocked events for trend analysis.

## Contain and prevent

Preserve WAF and origin logs, correlate request IDs, and verify the affected application version and patch status.

Reduce exposure, maintain a patch SLA and monitor WAF policy changes.

## Knowledge check

- What does the WAF verdict show?
  - The simulated request was blocked
  - The server was definitely compromised

<details>
<summary>Answer and rationale</summary>

The simulated request was blocked. Blocked activity supports triage, while origin evidence establishes impact.

</details>

- Which source helps check impact?
  - Endpoint wallpaper policy
  - Correlated origin application logs

<details>
<summary>Answer and rationale</summary>

Correlated origin application logs. Origin logs can show whether the request reached and affected the service.

</details>

## Validation and mapping

Baseline and noisy fixture produce no alerts. The positive fixture produces an alert with linked evidence.

The fixture contains a classification only. It contains no request payload or evidence of successful exploitation.
