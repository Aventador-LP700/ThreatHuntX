# 36 · Container Escape

Inspect an audit projection that records potentially dangerous host access requested by a workload.

**Track** Advanced · 15 min · Kubernetes

**Prerequisites** Know the basics of Kubernetes auditing and how to review authorization context.

## Investigate

**Attacker intent** Cross container boundary.

**Learning outcome** Review workload actor, namespace, pod privileges and API admission result. Compare authorized runtime observations.

1. Review the clean baseline. Kubernetes audit projection supplies the exercise evidence.
2. Consider the hypothesis. A workload-created privileged pod requesting the host PID namespace should trigger review of authorization and runtime evidence.
3. Replay the positive fixture and inspect THX-36. Review workload actor, namespace, pod privileges and API admission result. Compare authorized runtime observations.
4. Compare the noisy fixture. Infrastructure monitoring or storage agents can require host-level access.

## Rule and evidence

Count at least 1 observation(s) per `host` inside 300 seconds. Each distinct source record can count once.

| Field | Comparison | Value |
| --- | --- | --- |
| `action` | `eq` | `"create_pod"` |
| `observables.privileged` | `eq` | `true` |
| `observables.host_namespace` | `eq` | `"pid"` |
| `observables.actor_class` | `eq` | `"workload"` |

Tuning guidance. Scope approved infrastructure exceptions by namespace, service account and workload identity.

## Contain and prevent

Preserve audit and workload definitions, stop unauthorized workloads via approved procedures and assess host exposure.

Use Pod Security Standards, scoped admission exceptions and independent runtime monitoring.

## Knowledge check

- What raised concern together?
  - Privilege and host PID access
  - The presence of an application namespace

<details>
<summary>Answer and rationale</summary>

Privilege and host PID access. A privileged workload with host namespace visibility has broader reach.

</details>

- What would help confirm host effects?
  - The pod name alone
  - Independent runtime and host audit evidence

<details>
<summary>Answer and rationale</summary>

Independent runtime and host audit evidence. An admission record describes configuration. Runtime evidence supports impact.

</details>

## Validation and mapping

Baseline and noisy fixture produce no alerts. The positive fixture produces an alert with linked evidence.

Exposure is an indicator, not evidence of an escape. No Kubernetes resources are created by replay.

Enterprise ATT&CK 20.1 · related. The exercise observes a risky configuration associated with potential escape. It does not reproduce escape or prove it occurred.
