# 27 · Device-code phishing

Inspect device-flow sign-in records for successful use on an app outside an expected device policy.

**Track** Intermediate · 12 min · Identity

**Prerequisites** Be comfortable reading timestamps and entra sign-in or audit projection fields.

## Investigate

1. Review the clean baseline. Entra sign-in or audit projection supplies the exercise evidence.
2. Consider the hypothesis. An unmanaged device-flow grant to an unapproved application merits checking user intent and policy.
3. Replay the positive fixture and inspect THX-27. Locate application ID, flow type, device posture and user, then review follow-on token use by that application.
4. Compare the noisy fixture. Headless device onboarding and some administrator tools legitimately use device flow.

## Rule and evidence

Count at least 1 observation(s) per `user` inside 300 seconds. Each distinct source record can count once.

| Field | Comparison | Value |
| --- | --- | --- |
| `action` | `eq` | `"oauth_grant"` |
| `outcome` | `eq` | `"success"` |
| `observables.flow` | `eq` | `"device_code"` |
| `observables.device_class` | `eq` | `"unmanaged"` |
| `observables.app_trust` | `eq` | `"unknown"` |

Tuning guidance. Constrain allowed applications and devices, and sample approved flows to make narrow exceptions.

## Contain and prevent

Confirm the user initiated the action, revoke suspicious sessions and review the associated application activity.

Limit device authorization flow to approved applications with conditional access and user education.

## Knowledge check

- What provides context beyond the flow type?
  - Application trust and device posture
  - The size of the sign-in table

<details>
<summary>Answer and rationale</summary>

Application trust and device posture. Device flow is legitimate for some applications. Context identifies unexpected use.

</details>

- What should you ask the account owner?
  - Whether they know the event ID by heart
  - Whether they initiated the device authorization

<details>
<summary>Answer and rationale</summary>

Whether they initiated the device authorization. User intent helps distinguish phishing from a sanctioned grant.

</details>

## Validation and mapping

Baseline and noisy fixture produce no alerts. The positive fixture produces an alert with linked evidence.

The grant may reflect abuse without showing the delivery mechanism. No codes or tokens are present.

Enterprise ATT&CK 20.1 · related. T1566.002 represents link-based phishing delivery that can lead to a device grant. The fixture observes the grant only.
